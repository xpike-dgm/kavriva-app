# T-E3-007 — Direct-path bypass negative tests

1. objective: Detect generic-client routes that would bypass E3/E5 for another user's maintenance result or private object.
2. outcome-link: FL3.1.4/F3.1.4, ADR-006 Decision 9 — client paths carry no high-consequence mutation or private-object authority.
3. preconditions + completed dependencies: T-E3-006a, T-E3-006b and T-E3-006c are DONE for their inventory/contract scopes. T-E3-001-R1 remains REVIEW.
4. mandatory reads: planning task index, dependency graph, ADR-006 Decision 9, DEC-0068/0069, task execution protocol; the three predecessor records and inventories, browser profile, E3/E5 manifests, migrations, current official Supabase Data API and Storage access guidance.
5. allowed paths: E3 test files, the E3 local-Auth CI workflow, this pack, `[[vault/REGISTRY/T-E3-007.md]]`, `[[vault/EVIDENCE/E-DEV-011.md]]`, and generated registry/routing indexes.
6. forbidden areas: Hosted bucket/policy/secret/user writes, public client grants, production redirects, privileged browser activation, E3/E5 product authority changes, and a T-E3-001-R1 DONE claim.
7. expected artifact changes: A repeatable isolated Supabase private-bucket and direct Data API probe, PostgreSQL role and cross-tenant operation negatives, plus evidence distinguishing test fixtures from hosted proof.
8. acceptance + negative cases: A second user cannot claim a motorcycle or learn another actor's operation result. Client SQL roles cannot read/write private E3/E5/audit rows or inherit the server role. A real private test bucket contains a server-written object; anonymous and signed-in generic clients cannot read, list, upload, delete, transform or issue a signed URL for it. Direct Data API attempts selecting private schemas fail. Any service-key or `postgres` console capability is treated as privileged administration, never as a product authorization PASS.
9. validation / architecture / integration checks: Local E3 PostgreSQL suite, isolated Supabase CI with Storage and PostgREST, E10 `run_all.py`, reproducible generated indexes, PR CI and independent task-level review. The local machine has no Docker, so the container probe must run in CI.
10. migration / rollback needs: No migration or hosted change. Revert tests/workflow through a PR if needed; test bucket exists only in disposable CI containers.
11. responsive / accessibility rules: N/A; no screen change.
12. evidence + handoff format: `[[vault/EVIDENCE/E-DEV-011.md]]` records checks, fixture assumptions and residual hosted/Studio boundaries.
13. graph-update records: `[[vault/REGISTRY/T-E3-007.md]]` is DONE for the owner-accepted negative-test scope; regenerate registry/routing indexes. Do not advance T-E3-001-R1.
14. escalation rules: If the local or hosted client unexpectedly reads or mutates private data, keep affected capability HELD and correct the access path before any production activation. A privileged Dashboard/SQL editor role requires separate custody and access review; these client-role tests cannot prove it safe.
